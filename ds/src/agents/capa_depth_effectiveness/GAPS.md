## Risk assessment intentionally dropped from CAPA depth classification
As of 2026-07-14, `CAPADepthClassification` classifies the proposed CAPA against the GQA/070 Hierarchy table only (`hierarchy_level`, `hierarchy_level_label`, `hierarchy_rationale`) — it no longer extracts the report's Risk Assessment/RPN section or checks whether the CAPA depth is commensurate with risk. This was a deliberate scope decision (user: "we need to refer only the rankings table from SOP GQA/070, I don't think risk assessment is needed"), not an oversight.

Worth being aware of: GQA/008 §6.1.2.2 (the rule that established using the CAPA Hierarchy at all) reads *"...to identify appropriate CAPA commensurate with the associated risk"* — i.e. the SOP itself pairs depth with risk. Dropping risk assessment means this endpoint can say *what* Hierarchy level a CAPA sits at, but not whether that depth was *appropriate* for the situation (e.g. a Level 2 CAPA on a high-severity, recurring event would previously have been flagged; it no longer is). The `is_depth_commensurate_with_risk`/`risk_level`/`risk_extraction_confidence` fields, the `reconcile_commensurate_flag` guardrail, and the risk-extraction logic in `capa_depth_system.txt` were all removed. The earlier investigation into risk/RPN extraction reliability (checkbox tables like `464366_OOS.docx` not rendering as legible text vs. plain-text statements like `448289_RCI Report.docx`) is no longer relevant to this endpoint's scope, though it may resurface if risk-commensurate-checking is reintroduced later, e.g. as a separate endpoint or a follow-up field.

## Effectiveness Check time horizon has no fixed default
The SOPs do not mandate a specific monitoring duration/batch count. Real reports vary (observed: 3, 5, 10 batches). The prompt instructs the model to extract exactly what's stated and return an empty string when the report is silent — it must never invent a default.

## monitoring_method is not schema-constrained
`EffectivenessCheckExtraction.monitoring_method` is typed as a plain `str`, not a `Literal[...]` of the 9 SOP GQA/008 Table 4 methods (Auditing, Spot Check, Sampling, Monitoring, Trend analysis, Periodic product review, Surprise Audit, Periodic Checks, Verification of Validation Reports) plus the `"Not clearly classifiable"` fallback. The 10-value constraint currently lives only in the prompt text (`effectiveness_check_system.txt`). ## Report format variance (table vs. prose)
The majority of reports use structured tables for the CAPA action and Effectiveness Check Plan sections; a minority (e.g. `441957_RCI_Report.docx`, `448289_RCI Report.docx`) present the same content as prose paragraphs. The full-document-text + LLM extraction approach was chosen specifically to handle both without brittle per-section table parsers, but this hasn't been validated at scale — spot-check table-format and prose-format reports separately to confirm extraction quality doesn't degrade on either.

## Rule 1/2/3/4 reliability fixes (2026-07-15)
A live-run investigation across 7+ reports found four distinct reliability bugs in the rule critique logic, all now fixed with deterministic Pydantic validators (not prompt-only, since prompting alone proved insufficient — same lesson as `monitoring_method`):
- **Rule 1 (SMART/Time-bound)** never had a grounded signal — it was inconsistently substituting the effectiveness-check's `time_horizon` (the monitoring PERIOD) for the CAPA action's own due date (a different field, previously not extracted at all). Fixed by adding `capa_due_date` to `EffectivenessCheckExtraction` and a validator (`_rule1_due_date_consistency`) that rejects-and-retries if the due date is blank/a bare placeholder and Rule 1 wasn't flagged.
- **Rule 2 (Effectiveness Plan Identified or Rationale Given)** passed on bare "NA"/"Not applicable" placeholders with no actual justifying clause. Fixed with `_rule2_bare_placeholder_consistency`, using a word-list heuristic (`_is_bare_placeholder`) to detect quotes with no substantive content.
- **Rule 3 (Sufficient Data Points)** double-counted the same "nothing is stated" defect alongside Rule 2 when the EC section was entirely absent. Fixed with `_rule3_not_applicable_when_no_plan`, which silently clears Rule 3 whenever Rule 2 has already failed (Rule 2 failing means, by definition, no plan exists at all — Rule 3 has nothing to judge).
- **Rule 4 classification** defaulted to "(c) CAPA rationale" as a catch-all in 6/7 live runs, even when the quoted text was just a plain CAPA description or root-cause statement with no actual justificatory language. Fixed via prompt tightening only (no clean deterministic signal exists here) — verdict was never affected, only the internal-reasoning label.

The `_is_bare_placeholder` word-list (`na`, `n/a`, `not`, `applicable`, `none`, `nil`, `present`, `stated`, `required`) hasn't been stress-tested against all 50 historical reports' placeholder phrasings — worth widening if a future report's genuine "nothing stated" wording slips through unflagged, or a real short rationale gets misclassified as bare.

## Generated Effectiveness Plan (2026-07-15/16) — new capability, now a genuinely independent 3rd LLM call
Per updated requirement: section 12 (Effectiveness Check Plan) exists in historical reports but may not be authored in future reports, so the endpoint also **generates** an independent SOP-grounded plan (`generated_plan`) alongside the existing extraction — always produced, regardless of whether the report already has a section 12, so a reviewer can compare the human-authored plan against what SOP 6.1.2.1/6.1.2.4/6.1.3.2/Table 4 would suggest. `generated_plan` is never run through the Rules 1-4 critique (critiquing a plan the model just generated to satisfy those same rules would be circular).

**Architecture (as of 2026-07-16):** originally `generated_plan` was produced by the SAME LLM call as `extraction`/`rule_critiques` (one call reading the full report), with prompt instructions telling the model not to copy section 12. A live investigation across 7 reports found this insufficient — `generated_plan.monitoring_duration` consistently echoed the report's real section-12 value (exact or near-exact match on 4 of 6 reports tested), most likely because the same call had already written that real value into `extraction` moments earlier in its own output, biasing the "independent" draft that followed. Prompt wording alone couldn't prevent this (same lesson as the Rule 1/2 fixes above: instructions aren't a substitute for structural guarantees).

Fixed by physically splitting into three independent parallel LLM calls (see `capa_depth_effectiveness_route.py`):
1. `capa_depth` — unchanged, reads the full report.
2. `effectiveness_check` (schema `EffectivenessCheckExtractionAndCritique`) — reads the full report (section 12 included), produces `extraction` + `rule_critiques` only.
3. `generated_plan` (schema `GeneratedEffectivenessPlan`, prompt `generated_effectiveness_plan_system.txt`) — reads a copy of the report with section 12 **physically removed** by `strip_section_12()` (regex-based: finds the last "effectiveness check plan" heading — skipping table-of-contents references — and removes everything up to the next "List of Annexures/Attachments" heading, replacing it with a redaction note). For PDFs, this requires local text extraction via `pypdf` (`extract_pdf_text`) purely to produce this redacted excerpt — the other two calls still read the native PDF file directly via upload, unchanged.

The route assembles the final `EffectivenessCheckResult` (a plain combining container, no validators of its own) from the two calls' results after both complete. Cost/latency tradeoff accepted knowingly: one extra LLM call per analysis, in exchange for a genuine (not instruction-based) independence guarantee.

Validated live on `459682_OOT.docx` pre-split (deep ground truth available): the generated plan's `grounding.preceding_evidence_quote` and `effectiveness_criteria` converged closely on the real Section 12 content (CpK baseline of 0.61/1.46/0.84, "CpK improvement" category, QA responsible) — drafted from the report's earlier "Quality attributes review" section. In retrospect this convergence is ambiguous evidence given the anchoring bug discovered afterward; needs re-validation post-split to confirm it reflects genuine reasoning and not residual copying.

Not yet re-validated post-split: whether `grounding.preceding_evidence_quote` reliably returns "not available" (rather than a non-quantitative sentence) when no real baseline exists — this was observed as a minor gap pre-split on `RCI - Griseofulvin.pdf` and hasn't been re-checked with the redacted-input architecture.

Also inherits an existing simplification: like `EffectivenessCheckExtraction`, `generated_plan` is a single combined object even when a CAPA bundles multiple distinct actions (see `459682_OOT.docx`, which has two actions) — it drafts one holistic entry rather than one row per action, mirroring the current extraction's granularity rather than `CAPADepthClassification`'s per-action list. Revisit if per-action effectiveness plans are ever required.

## Generated monitoring duration/batch count (2026-07-16) — heuristic, not SOP-derived
The user asked for the monitoring duration/batch count to actually be generated (reversing the initial "leave blank" decision above). Re-reading the SOP surfaced Table 4 ("Guideline for the assessment of effectiveness check," advisory "should" text under 6.1.3.1/6.1.3.3, not a "shall" rule): duration should scale with risk severity and whether the fix is an "engineered solution" — higher risk + engineered fix + high detection probability warrants a shorter window, fewer observations needed for confidence.

`generated_plan.monitoring_duration` is calibrated from: (a) the report's own Risk Assessment/RPN section if present, and (b) an independently-judged engineered-vs-procedural read of the CAPA fix, reasoned directly within the dedicated `generated_plan` call (see architecture note above) — it does NOT consume `capa_depth`'s computed hierarchy_level (that remains a fully independent parallel call).

**Two rounds of fixes were needed before this actually worked:**
1. Splitting `generated_plan` into its own call with section 12 redacted (see above) fixed the anchoring-on-the-real-value bug, but immediately surfaced a second bug: post-split, a 6-report batch spanning genuinely different risk levels (Level 1 through Level 4) ALL converged on the identical "10 batches or 90 days, whichever is earlier" value. Root cause: the prompt had only ONE worked example (a moderate-risk case) and used that exact same phrase as the explicit "no risk data" fallback default — one strong attractor, no evidence duration should ever look different.
2. Fixed by adding a forced discrete `duration_tier` field (`Literal["short (3-5 batches, ~30 days)...", "standard (5-8 batches, ~45-60 days)...", "extended (8-10 batches, ~60-90 days)..."]`) positioned between `duration_rationale` and `monitoring_duration` — the model must commit to a tier whose label states the numeric band, THEN write a specific number within that band. Also added a second, genuinely contrasting worked example (high risk + engineered fix → "short" tier) so the model has evidence duration should vary, not just one repeated anchor. Same lesson as the earlier `monitoring_method` CpK-bias fix: free-form reasoning that should drive a value doesn't reliably do so — forcing a discrete intermediate commitment does.

Validated live on 6 reports spanning Level 1 through Level 4 risk: durations now genuinely vary (6-10 batches, tracking the cited risk level in the right direction — extended/8-10 for Level 1-2, standard/6 for Level 3-4). `490079_MC.pdf`'s Level 4 case correctly stayed at "standard" rather than jumping to "short," since its fix is procedural rather than engineered — confirming the tier gating correctly requires both high risk AND an engineered fix for "short," not risk alone.

Not yet validated: none of the 6 reports tested combine high risk with a genuinely engineered fix, so the "short" tier has never actually fired live — only inferred from the worked example and the correct non-firing on `490079_MC.pdf`. Still no clean report identified for this (checkbox-table risk sections make it hard to find via static plain-text scanning, though the model itself reads them correctly at generation time) — worth testing against more of the 50 historical reports, or accepting this as an unvalidated edge case until a real one surfaces.

## monitoring_duration was batches-only; now states both batches and days (2026-07-16)
Live testing found `monitoring_duration` returned ONLY a batch count in all 6 tested reports (e.g. `"6 batches"`), never a day-based value — even though each `duration_tier` label already states a day range too (e.g. `"short (3-5 batches, ~30 days)"`). Root cause: the only worked examples and the schema/prompt's own inline examples for this field showed batches-only (`"4 batches"`), so the model had no demonstrated reason to surface the day figure that was sitting right there in the tier it had just picked — same anchoring lesson as the original single-value bug above, just shifted from "one repeated value" to "one repeated unit."

Checked the historical reports for the real-world pattern before fixing (per direct request): of 6 concrete duration mentions found across the 50-report set, 4 were batches-only (`"05 batches shall be monitored"`, `"10 batches shall be monitored for assay"`, `"three consecutive batches"` ×2), 1 was days-only for an unrelated context (analyst requalification period, not batch monitoring), and 1 was the compound form (`459682_OOT.docx`: `"90 days or 10 batches whichever is earlier"`). So batches-only is the dominant real convention, but the compound form is the one clear precedent for exactly this "don't leave production-frequency risk unhandled" case.

Fixed by requiring `monitoring_duration` to state both units drawn from the already-defined tier band, phrased as `"<N> batches or <M> days, whichever is earlier"` (matching the `459682_OOT.docx` precedent) — no new judgment axis needed, since the day range was already sitting unused in each tier's own label. Validated live on 3 reports: all returned compound values correctly bounded within their tier's band (e.g. standard tier → `"6 batches or 60 days, whichever is earlier"`).

## Full 50-report empirical study: real duration vs. risk level vs. fix type (2026-07-16)
Ran a 5-agent parallel research pass across all 50 historical reports (not just spot-checks) to see whether real QA authors' effectiveness-check durations actually correlate with risk level and engineered-vs-procedural fix type the way SOP Table 4 (and this module's `duration_tier` logic) assumes. Per explicit user decision, this was findings-only — no code changes from this study alone.

Findings:
- **Only 16 of 50 reports (32%) state a real, quantified duration at all.** The rest split into ~14 reports with no CAPA whatsoever (root cause unassignable, or existing controls judged adequate) and ~20 reports with a real CAPA but an unspecified effectiveness-check duration (qualitative criterion only, no count). That second group is the actual target scenario for `generated_plan` — it's the majority case among reports that have a real CAPA, not an edge case.
- **The risk/engineered-vs-procedural correlation is real but only clean at the extremes.** At Level 4 (the highest risk seen with duration data), an engineered fix (`HIGH SCORING 2.pdf`, RPN 50) got a real 3-batch duration while a procedural fix at similar/lower risk (`490079_MC.pdf`, RPN 30) got 10+ batches — matching Table 4 exactly. But among the 13 comparable Level 1-3 reports, the same risk level and same fix type produced wildly different real durations (e.g. two Level-3/RPN-15 engineered fixes: one real report used 3 batches, another used 10 batches/90 days) — no clean pattern; likely driven by per-investigator judgment or company convention rather than a formula.
- **Zero of the 16 comparable reports had our tool's generated duration exactly match the real one** — expected and correct, since matching would mean the redaction-independence fix (above) had failed, not that it succeeded. Generated values do land in the same realistic order of magnitude as real ones (single-digit-to-low-teens batches, tens-of-days windows).
- **Real durations cluster bimodally around 3 or 10 batches**, not a smooth gradient — if the tier bands are ever revisited, discrete anchors might reflect practice better than the current continuous 3-5/5-8/8-10 gradient. Not changed, per the "findings only" decision.

## duration_tier "extended" collapses to one value regardless of report specifics (2026-07-16, fixed)
Testing 12 reports against the current pipeline found 9 of them returned the IDENTICAL `monitoring_duration` (`"8 batches or 60 days, whichever is earlier"`) despite citing different specific risk data (RPN 1 vs RPN 3) in `duration_rationale`. Root cause: the prompt has worked examples for "short" and "standard" tiers (added when the original single-value anchoring bug was fixed) but never got one for "extended" — so there's no demonstrated evidence the number should vary *within* a tier, only *across* tiers.

First fix attempt (present-vs-absent risk data) was insufficient: re-testing 6 reports that all had SOME risk data present (Level 1 or Level 2) still all collapsed to the same number, since that framing only distinguished "data present" from "no data at all" — it didn't address two different RPN values (1 vs 3) both counting as "present."

Second fix: reworded the guidance to position the number proportionally within a tier's band based on the actual cited RPN, not just which tier it falls in. Validated live on 6 reports: RPN 1 reports (`472927`, `485908`, `488822`, `491726`) consistently returned `"8 batches or 60 days"` while RPN 3 reports (`463568`, `470657`) consistently returned `"10 batches or 90 days"` — genuine variance.

**Third fix (2026-07-16, shipped) — corrected a direction bug found in the second fix.** Validating an unrelated live output surfaced that the second fix's direction was internally inconsistent: it mapped LOW RPN within "extended" (e.g. RPN 1) to the tier's SHORT/lower end (8 batches) and HIGH RPN within "extended" (e.g. RPN 9) to the tier's LONG/upper end (10 batches) — backwards from the cross-tier principle (higher risk → shorter duration overall). This created a "sawtooth": duration would climb as RPN rose from 1 to 9, then suddenly drop hard crossing into "standard" at RPN 10. Corrected so duration decreases monotonically across the ENTIRE risk spectrum, both within and across tiers: the lowest RPN in a tier's own range now gets that tier's longest/upper-end value, the highest RPN in a tier's range gets that tier's shortest/lower-end value (closest to the next, shorter tier) — added explicit RPN sub-bands (thirds) for all three tiers, not just "extended", plus fixed a related smaller gap: `preceding_evidence_quote` was capturing only a partial subset when several related values are stated together (e.g. 2 of 3 CpK figures) — now instructed to capture the full set.

Re-validated live post-fix: RPN 1 (`472927`) now correctly returns the tier's upper end (`"10 batches or 90 days"`); a Level 3/RPN 15 report (`459682_OOT`) lands within "standard"'s band as expected, though not hitting the exact prescribed sub-bucket precisely (soft prompt guidance, not a hard validator, so some looseness is expected by design). Reports sharing a narrow RPN sub-bucket (e.g. RPN 1 and RPN 3, both in the "1-3" bucket) legitimately still share a value — this is expected coarse-graining from only having 3 sub-bands per tier, not a regression of the original collapse bug (which spanned 9 reports across RPN 1 to 30, multiple tiers, all producing one identical value). Not yet verified whether "short" tier's sub-bands behave correctly on a real report (only demonstrated via worked example so far, same caveat as the tier itself never having fired live).

## generated_plan now gates on whether a CAPA exists at all (2026-07-16)
Investigating the "no duration cited" reports above surfaced a real bug: `generated_plan` had no way to detect that a report has NO CAPA at all (~14 of the 50), and would draft a full plan — including a fabricated `monitoring_duration` — regardless. Confirmed live on `RCI - Cholecalciferol - 2D matrix code error.pdf`: the research agent read its CAPA table as explicitly "no CAPA recommended," yet an earlier live test of this same report generated a full duration-bearing plan anyway. (Muddying this specific example: `capa_depth`'s own independent read of the same report concluded a real Level 5 CAPA *does* exist — the report's phrasing may itself be genuinely ambiguous — but the underlying gap, that `generated_plan` had no applicability check at all, is real regardless.)

Fixed by adding `applicability_reason` + `applicable` as the first two fields (reasoning-before-verdict, gating the whole plan) — `applicable` is "no" ONLY when section 11 has no genuine CAPA action at all. Per explicit user distinction: a report where a real CAPA exists but *this report's own* Section 12 waived/deferred its effectiveness check is NOT "not applicable" — that CAPA still gets a full plan drafted normally, since SOP 6.1.2.4 calls for an effectiveness plan (or a rationale) regardless of what the original authors decided. When `applicable` is "no", every other field (including `duration_tier`, which gained a 4th literal option "not applicable...") must be empty, enforced by a new `_not_applicable_consistency` validator. Not yet live-verified against a real Category-A report post-fix — next step.

## duration sub-band logic broke down on "demoted" reports (2026-07-16, fixed)
Validating 5 reports pasted together in one batch found `490079_MC.pdf` (Level 4, RPN 30 — high risk) landed on `duration_tier: "standard"` correctly (its fix is a checklist/inspection-record revision, not a genuine engineered change, so "short" is correctly denied), but the model's own stated reasoning — "RPN 30 is at the low end of the Level 4 band, so upper end of standard range selected" — produced `"8 batches or 60 days"`, the LONGEST duration observed across all 5 reports validated that day, for the single HIGHEST RPN among them. That's backwards: the prompt's sub-band instructions only covered RPN values that fall naturally *within* a tier's own stated range (e.g. RPN 15 naturally sits in "standard"'s 10-26 range); they never addressed what should happen when a report is pulled DOWN a tier by the engineered-vs-procedural gate, since RPN 30 doesn't literally belong to "standard"'s own range at all — it's an escapee from "short" (RPN >=27).

Fixed by adding an explicit "demoted report" case: when the cited RPN would, on its own, sit in a higher-urgency tier's range but gets pulled down because the fix isn't genuinely engineered, treat it as an escapee and force it to the SHORTEST/lower-end value of the tier it lands in — never the upper end, and never longer than a report whose RPN puts it in that tier normally. Added a new worked example (Example 2b: RPN 30, procedural checklist fix, demoted from "short" to "standard", correctly landing on "5 batches or 45 days" — the lower end — contrasted directly against Example 1's genuinely-low RPN 15 case, which correctly gets the upper end, "7 batches or 55 days"). Prompt-only fix, consistent with the "tighten prompt guidance only" approach chosen earlier for similar softness issues.

Re-validated via an isolated single-call script (bypassing `capa_depth`/`effectiveness_check` to test `generated_plan` alone): `490079_MC.pdf` (RPN 30, procedural fix) correctly returned `duration_tier: "standard"` and `"5 batches or 45 days"` — confirmed fixed.

**Second bug found from the same report, in a separate pipeline run.** The user re-ran the full pipeline (via `Depth_EC.docx`) shortly after and `490079_MC.pdf` came back with `duration_tier: "short"` this time — despite `duration_rationale` in that same response explicitly stating the fix is "a mix of procedural controls and maintenance-system updates rather than a single fully engineered physical interlock, so it does not justify the shortest 'short' duration." The tier field contradicted its own rationale. Root cause: the tier is literally named "short", and the model appears to conflate the TIER NAME with the English adjective "a short/tighter monitoring window" — reasoning that procedural-but-still-fairly-risky cases deserve "a conservative short window," then mistakenly writing the literal tier label instead of "standard." This is a distinct bug from the demotion/positioning one above — that one was about *where within a tier* a demoted report lands; this one is the model picking the *wrong tier entirely*, despite its own stated reasoning arguing against it.

Fixed by (a) restating the "short" gating requirement as a strict AND of all three conditions with explicit "ALL THREE" emphasis, (b) adding a direct instruction: if `duration_rationale` describes the fix as procedural/mixed/checklist-based, `duration_tier` must NOT be "short" no matter the RPN, and (c) explicitly warning that "short" is a tier name, not shorthand for "give this less time." Re-validated live, run twice in a row: both runs now correctly return `duration_tier: "standard"` (not "short") with `"5 batches or 45 days"` for this same RPN-30/procedural case. Both fixes are prompt-only; `duration_tier` remains a hard 4-way `Literal` with no cross-field validator checking it against `duration_rationale`'s free text — if this class of tier-vs-rationale contradiction recurs, the more robust fix would be a discrete `engineered_or_procedural: Literal["engineered", "procedural", "mixed"]` field ahead of `duration_tier` that a validator could check against, mirroring the existing `_rule4_consistency`/`_not_applicable_consistency` pattern — not implemented yet since two consecutive live re-tests came back clean.

## preceding_evidence_quote grabbing Risk Assessment/RPN legend text instead of a defect baseline (2026-07-16, fixed)
Validating `RCI - Griseofulvin.pdf`'s `generated_plan` found `preceding_evidence_quote: "\"Level 3 (RPN >=10<27)\""` — the risk-level BAND LABEL/legend text, not a quantitative baseline about the actual defect (there's no CpK/defect-rate/yield figure for this LIMS-calculation root cause, so the correct value here was "not available"). Root cause: the field's own instruction told the model to search "root cause analysis, trend/historical review, risk assessment, quality attributes review" for a quantitative baseline — explicitly including "risk assessment" as a valid source, which is exactly where the RPN/Level scoring lives. The model treated the Level/RPN band label as if it were a legitimate quantitative baseline, when it's actually risk-scoring metadata meant only for `duration_rationale`, not for grounding the effectiveness criteria. Didn't cause visible harm downstream (the generated `effectiveness_criteria` stayed qualitative and wasn't corrupted by the bad quote), but it's a real field-misuse bug.

Fixed by removing "risk assessment" from the list of sections to search, adding "about the DEFECT/FAILURE ITSELF" to the instruction, and explicitly telling the model NOT to use the Risk Assessment/RPN section as a source here — a risk score or its Level/RPN band label is a risk-scoring category, not a quantitative baseline, and belongs only in `duration_rationale`. Re-validated live via the isolated `generated_plan` script, run twice against `RCI - Griseofulvin.pdf`: both runs now correctly quote genuine defect-related data instead (impurity spec percentages in one run, a batch-specific recalculation failure note in the other) — no more risk-legend text. Prompt-only fix.
