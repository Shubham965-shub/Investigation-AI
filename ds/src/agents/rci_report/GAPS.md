**Bug found during this live run, root-caused and fixed the same day**: History Review returned 0 rows / `no_similar_events_found=True`, but `semantic_search_node` logged `column reference "deviation_id" is ambiguous` for both search fields — a real DB query error, not a genuine empty result.

Root cause, in `search_agent/api/services/filters.py`'s `build_filter_clause`: the `exclude_id` filter (added 2026-08-06, see entry below) emits an unqualified `"deviation_id"::text != $N`. `semantic_search.py`'s `_build_from_clause()` joins the details table (aliased `t`) to the vector table (aliased `v`) `ON t."deviation_id" = v."deviation_id"` whenever `SEARCH_DETAILS_TABLE` is configured — which it is in this environment (`investigation_ai_sample_test`). Both sides of that join then have a `deviation_id` column, so the unqualified reference is genuinely ambiguous to Postgres. Every *other* filter in that file (`qe_type`, `date_from`/`to`, `locations`, etc.) is unaffected — those columns only exist on the details table `t`, not on the 6-column vector table `v`. `exclude_id` is the only filter that names the join key itself, which is why it's the only one broken.

**This retroactively invalidates the "confirmed working" claim in the 2026-08-06 entry below.** That entry's "Re-ran live: History Review correctly returns 0 rows... again" was not evidence the self-match exclusion worked — it was this same SQL error being thrown and silently swallowed by `semantic_search_node`'s `except Exception` handler, producing an empty result that happened to look like the expected post-fix state. The self-match exclusion had never actually been exercised successfully until today.

Fixed: qualified the fragment with `t.` (`filters.py`) — always a valid alias for this column, whether or not a details table is joined in. Verified two ways: (1) direct re-run against deviation_id=476050 — before the fix, `rows: 0, no_similar_events_found: True` with the ambiguous-column error logged; after, `rows: 15, no_similar_events_found: False`, no error logged, and — critically — **476050 does not appear among the 15 rows**, confirming the self-match exclusion is now genuinely working, not just coincidentally empty. (2) Full repo test suite re-run: same 89 passed / 17 pre-existing failures as before this fix, no regressions. This is a `search_agent`-level fix (no GAPS.md exists there yet), so it also fixes `exclude_id` for any future caller beyond `rci_report`'s History Review, which remains the only current one.

## 2026-08-06 — Section 11 produced only one consolidated row where the real UI wants one row per CAPA action

User-provided screenshot of the real production UI's Section 11 showed 2 rows (one per CAPA action: SOP F1/PR/003 revision, scratch-proof containers), but this module's generated output only ever had one. 2. **`RCAMethod` enum was missing two methods the real report explicitly named.** The real report states the RCA method as "Process Mapping tool, Gemba Walk and Failure Mode Effective Analysis (FMEA)" — but `RCAMethod` (`measure_analyze.py`) only offered `Why-Why Analysis`/`Fishbone / Ishikawa`/`Fault Tree Analysis`/`Flowchart / Process Mapping`/`Not explicitly stated`, forcing two different live runs to guess two different wrong single labels. Re-ran live: correctly returned `["GEMBA Walk"]` grounded in the actual input evidence, instead of misfiring on Fishbone/Flowchart.

Two other apparent findings from the same comparison turned out to be **test-fixture errors on the reviewer's part, not module bugs** — corrected here so this entry doesn't mislead a future reader:

## `manual_entries` has no confirmed source — RCI Report has no fill-in step of its own
`RciReportGenerationRequest.manual_entries` was designed assuming an investigator could type values in at RCI-Report time for fields with no TrackWise backing (MC's `primary_defect`/`nature_of_complaint`, OOS/OOT's `immediate_actions`, MC's whole equipment grid, etc.). That assumption is wrong: RCI Report is a generated artifact, not a form — there is no screen where a human fills in "the RCI Report" before it's produced. If this data is ever going to be non-empty, it has to be captured during an earlier workflow step (Problem Statement, Evidence Collection, Interview Questionnaire) and carried forward by the backend into this request — and nothing in either repo currently does that carrying-forward. Until that's built, every field gated on `manual_entries` will deterministically render as `source="manual_entry_required"`, `value=""` (or an empty list, e.g. `initial_impact_assessment_system.txt`'s OOS/OOT `immediate_actions` handling) on every real request — this is not a hypothetical edge case, it's the expected steady state today. The prompts already degrade correctly to this explicit gap marker rather than fabricating content, so no code is broken by this — but treat every `manual_entry_required` field in a generated report as "reliably blank," not "occasionally blank," until the upstream carry-forward exists.
