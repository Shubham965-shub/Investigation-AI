## 2026-08-25 — Two more extraction bugs found validating against the actual genuine completed report (not just the earlier critique-annotation test document)

Follow-up to the entry below. The user asked to validate the whole RCI report generation against `RCI of Mycophenolate 500mg_ Amperage Deviation_R0.docx` — the genuine, human-completed report for record 505542 (real employee names/IDs, embedded charts, full batch-level data), a materially richer and more authoritative source than `505542_RC_Impact_CAPA.docx` (itself a critique/annotation document quoting the real report's content, used for all testing up to this point). Running the fixed extraction against this real document surfaced two more real gaps:

1. **Checkbox symbol and label text live in adjacent runs, not the same run.** `_detect_repeat_occurrence`'s symbol-based detection required a `<w:sym>` element and its "Yes"/"No" label text to appear in the SAME run (`for r_elem in tr...: sym = r_elem.find(sym); t_text = ...; if t_text and is_checked: ...`). Confirmed live: a real Word checkbox is structured as a symbol-only run (no text) immediately followed by a separate text run carrying the label. This meant the symbol-based check has likely never actually matched anything in this codebase — it always fell through to the plain-text fallback, even when a real checked checkbox was present. For 505542's real report, the checked "No" (Wingdings char F0FE, in `_CHECKED_SYMBOLS`) sits right before the text " No. If yes, Mention the details as:" — a genuinely correct, deterministic signal that was being discarded. Fixed by tracking the most recently seen symbol's checked-state as `pending_checked` and pairing it with the next run that actually carries a "yes"/"no" word, rather than requiring same-run co-location. Verified live: now correctly returns `False` for 505542 (matching the real checked checkbox), still correctly returns `None` for the other test document's unmarked "Yes No" plain-text placeholder (no regression).

2. **Heading matchers were keyed to the blank template's exact wording, not real report phrasing.** `_is_impact_assessment_heading` required "conclusion" or "batch disposition" alongside "impact assessment"; `_is_correction_remedial_heading` required both "correction" and "remedial". The real 505542 report uses shorter headings — "8 Impact Assessment:" and "REMEDIAL ACTION: Not Applicable." — neither matched, so `impact_assessment_text`/`correction_remedial_text` came back completely empty against this real document even after yesterday's fix. Broadened both matchers to accept the shorter real-world phrasing (still excluding false-positive risks: "initial"/"immediate action" for the impact heading, "capa"/"corrective" for the remedial heading). Separately, "REMEDIAL ACTION: Not Applicable." embeds its entire answer directly in the heading line with no body paragraph following at all — added inline-content extraction for this heading (mirroring the existing pattern already used for `problem_statement`), since heading text is otherwise never collected as content and this would have been silently lost. Verified live: `impact_assessment_text` (2220 chars, the real 8.1-8.11 content) and `correction_remedial_text` ("Not Applicable.") now both populate correctly against the real report; no regression on the other test document.

**Full end-to-end validation**: generated the complete 13-section RCI report for 505542 using this now-doubly-fixed extraction as the RC & CAPA source, alongside the RCI Plan and 6 real task reports already used this session. All sections generated with zero errors. Cross-checked against the real report: Root Cause taxonomy (Method/Process Deficiency), `is_repeat_occurrence` (False), and the CAPA table (description, responsibility=MSAT, due_date=25/10/2025) all matched exactly; Impact Assessment's 11 subsections structurally matched (10 of 11 correctly NA, batch-impact narrative synthesized reasonably). One discrepancy noticed in Risk Assessment (Repeatability scored "High" vs. the real report's "Low", traced to History Review's live search surfacing event 505548 — the *sibling* TrackWise record for this same underlying event, not a genuinely distinct prior occurrence, since `exclude_id` only excludes the one deviation_id passed in) — **user confirmed 2026-08-25 that Risk Assessment is not a required section for this work**, so this is not being tracked as an open item.

## 2026-08-25 — `extract_rci_report_sections` had two real bugs (heading conflation, table over-capture) found while wiring its output through to RCI Report generation for the first time

The user asked for RCI Report's Root Cause Conclusion, Impact Assessment, Correction/Remedial Action, and CAPA sections to be grounded in the most recent attempt of the uploaded RC & CAPA document, instead of thin critique summaries or TrackWise fields. Tracing the pipeline found `extract_rci_report_sections` (`api/services/rci_report_extraction.py`) already deterministically parses this document (no LLM) but only ever surfaces a fraction of what it extracts — `rc_conclusion_text` and CAPA content reach `critique_route.py`'s two endpoints, get flattened and LLM-condensed to a 3-4 sentence blurb, and that's the only trace that ever left ds. `is_repeat_occurrence` and structured `capa_items` were computed and discarded; Impact Assessment and Correction/Remedial text were never captured at all (their headings were used only as exit signals from the Root Cause state).

Fixing this surfaced two real, previously-undocumented bugs, both confirmed by running the extraction directly against a real uploaded RC & CAPA document (record 505542, `~/Downloads/505542_v2/505542_RC_Impact_CAPA.docx`):

1. **Heading conflation.** `_is_capa_heading()`'s clause `"correction" in tl and "remedial" in tl` matched the "Correction and or Remedial action" heading too, flipping the state machine into `"capa"` state 4 paragraphs before the real "Corrective Action & Preventive Action" heading. `capa_overall_text` for 505542 started with Correction/Remedial content, not CAPA content, before this fix.
2. **Table over-capture.** Once in the (incorrectly-early) `"capa"` state, every table encountered got parsed as CAPA action rows via `_table_to_capa_items`, with no check that it was actually the CAPA action table. For 505542, `capa_items` came back with 3 rows before this fix (the real CAPA action, plus the Interim Control Plan table's "Not Applicable" row, plus the CAPA Extrapolation table's "Not Applicable" row) — 2 of 3 were not CAPA actions at all. This directly explains why `backend/backend/services/rci_report_request.py`'s `_accepted_capa()` had `capa_items` permanently hardcoded to `[]` with a comment saying "no real accepted-CAPA-action source yet" — the real source existed inside ds, it just never survived long enough to be usable.

**Fixed**: removed the conflated clause from `_is_capa_heading`; added dedicated `"impact"`/`"correction_remedial"` states (with `_is_impact_assessment_heading`/`_is_correction_remedial_heading` matchers — the former explicitly excludes "initial"/"immediate action" so it doesn't false-match Section 2's earlier "Initial Impact Assessment & Immediate Actions" heading); added `_is_capa_action_table()` to classify tables by their own header row ("capa description", or "corrective action"+"preventive action") rather than by section membership alone — non-matching tables (Interim Control, Extrapolation, signature block) fold into `capa_overall_text` as readable text instead of being misparsed. Verified live: post-fix, `capa_items` has exactly 1 entry for 505542 (matching the real single CAPA action), `capa_overall_text` correctly starts with CAPA content, and `impact_assessment_text`/`correction_remedial_text` are cleanly captured and separated for the first time.

**Third bug found during the same verification pass**: the plain-text `is_repeat_occurrence` heuristic (`"yes" in tl and "no" not in tl.split("yes")[-1]`) misread 505542's real text — *"Determine if the root cause is a repeat occurrence Yes No. If yes, Mention the details as: Not Applicable"*, an unchecked template placeholder with two "yes" occurrences — as a confirmed `True`, because it split on the wrong occurrence of "yes". This bug already existed before today but had zero real-world consequence, since `is_repeat_occurrence` was computed and discarded before reaching anything downstream. Now that it's being wired through for real, a false positive here would have reached the generated report. Fixed by extracting a shared `_repeat_occurrence_from_text()` helper (used by both the table-row and paragraph extraction paths) that returns `None` (genuinely unknown) rather than guessing when the text is an unchecked "Yes No" pair, instead of defaulting to a confident answer. Verified live: 505542 now correctly returns `None` instead of the false-positive `True`; the downstream Root Cause Conclusion prompt then reasons about this itself from context (correctly inferring `is_repeat_occurrence=false`, citing the document's own "Not Applicable" repeat-occurrence line) rather than being handed a wrong deterministic answer.

**New response fields, additive only**: `RCConclusionCritiqueResponse` gained `rc_conclusion_text_raw`, `is_repeat_occurrence`, `impact_assessment_text`; `CAPACritiqueResponse` gained `capa_text_raw`, `capa_items: List[CAPAItemDetail]`, `correction_remedial_text`. The existing condensed `rc_conclusion_text`/`capa_text` fields (used for the dashboard summary card) are unchanged — same "add alongside, never replace" pattern already used for Task Critique's `task_findings`.

**One observation, not a bug**: 505542's own "Correction and or Remedial Action" text legitimately quotes the same CAPA action text a second time (the source document itself cites it under "Executive Summary - Remedial Action/Corrective Action & Preventive Action"). This produced a genuinely duplicated item across the generated Correction/Remedial and CAPA sections in the live test — correct behavior given what the real document actually contains, not an extraction bug. This may be specific to this document being a critique/annotation-style document (heavy with `[Source: ...]` citations quoting the same fact from multiple places) rather than a pristine investigator-authored template upload; worth re-checking against a second, more typical real upload if one becomes available.
